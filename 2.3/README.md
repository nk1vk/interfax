# Классификация обращений клиентов RUDATA (задача 2.2.3)

Прототип определяет по тексту обращения и логину клиента три поля из справочника —
**интерфейс, продукт и тематику**, — для каждого поля даёт оценку уверенности и признак
«нужна ручная проверка». Всё работает локально: тексты обращений никуда не передаются.

Сравниваются три подхода:

| Подход | Ноутбук | Как работает |
|---|---|---|
| 1. Классический | `classify_classic.ipynb` | TF-IDF + SVD + градиентный бустинг (LightGBM, XGBoost, CatBoost), подбор параметров Optuna |
| 2. Языковая модель | `classify_llm.ipynb` | локальная `qwen3:8b` через Ollama: определения классов из справочника и примеры в промпте; уверенность — вероятность ответа по данным модели |
| 3. Гибрид | `classify_llm.ipynb` | каждое поле определяет подход, лучший для него на validation; уверенность в интерфейсе и продукте — согласие LLM и бустинга |
| Всплески | `spikes.ipynb` | уведомления о нетипичном росте обращений по полям и их сочетаниям — по часам и по дням |

## Структура папки

```
2.3/
├── classify_classic.ipynb      подход 1: данные, EDA, признаки, бустинги, пороги, оценка
├── classify_llm.ipynb          подходы 2 и 3, сравнение трёх подходов на test
├── spikes.ipynb                выявление всплесков: метод, уведомления, ложные срабатывания, сквозной сценарий
├── service/                    сервис для заказчика: REST, пакетная обработка, всплески — со своей инструкцией
├── requirements.txt            библиотеки Python
├── data/raw/                   appeals.csv, dictionary.csv, описание данных, постановка задачи
├── models/                     сохраняются ноутбуками
│   ├── access.json             справочник «логин → подключённые продукты»
│   ├── classic_model.pkl       TF-IDF, SVD и модели бустинга
│   ├── classic_params.json     выбранные модели, параметры, пороги уверенности
│   └── llm_params.json         настройки LLM, промпт, пороги, состав гибрида
└── results/                    сохраняются ноутбуками
    ├── classic_*.csv           качество и прогнозы бустинга
    ├── llm_predictions_*.jsonl ответы LLM и уверенность по каждому обращению
    ├── llm_answers_*.jsonl     эксперимент с тремя запросами на обращение (не используется, см. ноутбук LLM)
    ├── comparison_test.csv     итоговое сравнение трёх подходов
    └── resources.csv           скорость и ресурсы
```

## Установка

Нужно: Python 3.12 или 3.13, Ollama свежей версии (нужна поддержка вероятностей токенов `logprobs`), около 10 ГБ на диске. Для LLM желательна видеокарта NVIDIA
от 8 ГБ памяти — на процессоре модель работает в разы медленнее.

### Windows

1. Python с python.org — при установке отметить «Add python.exe to PATH».
2. Ollama с ollama.com (установщик для Windows). После установки Ollama работает в фоне.
3. В командной строке, в папке проекта:
   ```
   py -m venv .venv
   .venv\Scripts\activate
   pip install -r requirements.txt
   ollama pull qwen3:8b
   ```
4. Проверка: `ollama list` показывает `qwen3:8b`; `nvidia-smi` показывает видеокарту —
   Ollama использует её автоматически.

### macOS

```
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
brew install libomp
ollama pull qwen3:8b
```

Ollama для macOS — с ollama.com.

Папку `.venv` нельзя копировать с другого компьютера: окружение создаётся заново на каждом.

## Запуск

Ноутбуки открываются в Jupyter (`jupyter notebook`) или VS Code с ядром из `.venv` и запускаются
целиком, по порядку:

1. **`classify_classic.ipynb`** — обучает бустинги и сохраняет справочник доступов, модели и прогнозы.
   Без этого шага второй ноутбук не запустится.
2. **`classify_llm.ipynb`** — размечает validation и test моделью и сравнивает три подхода.
   Ответы модели сразу сохраняются в `results/llm_predictions_*.jsonl`: если прогон прервать,
   при следующем запуске он продолжится с того же места. Чтобы разметить заново
   (например, после изменения промпта), эти файлы нужно удалить.

Если первый ноутбук уже выполнен на другом компьютере, достаточно перенести папки `models/` и `results/`
и запустить только второй.

Запуск без открытия ноутбуков (например, на ночь) — из папки проекта с активированным окружением:
```
jupyter nbconvert --to notebook --execute --inplace --ExecutePreprocessor.timeout=-1 --ExecutePreprocessor.kernel_name=python3 classify_llm.ipynb
```
Результаты записываются в ноутбук в конце выполнения, в окне командной строки ход расчёта не виден.
Сколько обращений уже размечено, показывает число строк в `results/llm_predictions_*.jsonl`:
`(Get-Content results\llm_predictions_validation.jsonl).Count` в PowerShell или
`wc -l results/llm_predictions_*.jsonl` в macOS.

## Основные настройки

Константы — в начале каждого ноутбука.

| Настройка | Где | Что значит |
|---|---|---|
| `N_TRIALS`, `TUNING_TIMEOUT` | classic | число попыток Optuna и лимит времени на подбор одной модели для одного поля |
| `SVD_COMPONENTS` | classic | до скольких столбцов сжимается TF-IDF |
| `TARGET_AUTO_ACCURACY` | оба | требуемая точность поля среди принятых автоматически; по ней выбираются пороги |
| `MODEL` | llm | модель Ollama |
| `AGREEMENT_FIELDS` | llm | поля, для которых уверенность гибрида — согласие LLM и бустинга |

## Правила обработки

- Конкретный продукт выбирается только из продуктов, подключённых логину; `NO_PRODUCT` и `UNKNOWN` доступны всегда
  (`UNKNOWN` — при 2+ подключённых продуктах, как в разметке).
- Если на выбор продукта повлияли доступы, это отмечается тегом `product_source = 'access'`.
- Нет уверенности в продукте (ниже порога) — продукт `UNKNOWN` (правило заказчика).
- Ручная проверка: `UNKNOWN` в любом поле, уверенность ниже порога поля или противоречие полей
  (например, интерфейс API с конкретным продуктом).

## Ограничения

- Данные синтетические. Правила согласованности полей и «API → NO_PRODUCT» — соглашения учебной разметки,
  на реальном потоке их нужно согласовать.
- Справочник доступов собран из `appeals.csv`. В рабочем сервисе доступы нужно брать из системы,
  где они ведутся, в момент поступления обращения. Неизвестный логин — ручная проверка.
- Уверенность модели — не откалиброванная вероятность, а оценка для выбора порога.
- Классы `UNKNOWN` и редкие тематики представлены небольшим числом примеров, оценки по ним неустойчивы.
