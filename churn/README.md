# 2.2.2. Раннее выявление риска расторжения договора (RUDATA)

По ежедневной активности клиента (запросы к API и сессии в продуктах) каждое утро оценивается
риск расторжения договора в ближайшие 28 дней. Цель — предупредить за 14–28 дней до ухода
и назвать до трёх наблюдаемых факторов риска.

Данные синтетические: 400 клиентов, 80 расторжений, период 2025-04-01 — 2026-09-30.

## 2. Файлы подробно

### `churn.ipynb` — основной ноутбук (1-й подход, обучение с учителем)

Весь проект от данных до модели, по разделам:

1. Постановка задачи и перевод на язык машинного обучения.
2. Загрузка данных и проверки (ключи, неизвестные клиенты, период выгрузки).
3. Исследовательский анализ: уходы по месяцам, доступы, активность перед уходом.
4. Дневная активность клиентов (`daily`) — календарь дней действующего договора, дни без активности = 0.
5. Новые признаки (`panel`) — 39 признаков, все только по дням до даты прогноза.
6. Целевая переменная: 1 — уход в ближайшие 28 дней, 0 — ухода не было, пропуск — исход неизвестен.
7. Разбиение по времени: train / valid / test (границы считаются от конца выгрузки).
8. Модели: логистическая регрессия и CatBoost, кросс-валидация по времени, подбор параметров optuna.
9. Порог тревоги, проверка на test, разбор ошибок, важность признаков, факторы риска.
10. **Сохранение модели в `models/`.**
11. Как перейти на корпоративные данные, выводы по проекту.

Читает: `data/raw/*.csv`. Создаёт: `models/churn_model.pkl`, `models/model_params.json`.

### `churn_anomaly.ipynb` — второй подход (без учителя) и сравнение

Детектор аномального поведения, которому не нужны размеченные уходы:
- **правило по личной норме** — риск = среднее падение активности клиента относительно его обычного уровня;
- **Isolation Forest** — ансамбль деревьев, ищет нетипичное падение активности.

Сравнивает оба варианта с моделью из `churn.ipynb` на тех же valid и test.

Читает: `data/raw/*.csv`, `models/churn_model.pkl`, `models/model_params.json`.
Использует функции из `churn_pipeline.py` (`load_data`, `build_daily`, `build_features`, `add_target`),
поэтому данные и признаки у обоих подходов гарантированно одинаковые.

### `churn_pipeline.py` — рабочий скрипт для заказчика

Только то, что нужно для работы модели, без графиков и анализа. Функции:

| функция | что делает |
|---|---|
| `load_data` | читает три CSV |
| `build_daily` | дневная активность клиента за дни действующего договора |
| `build_features` | признаки на утро каждой даты (тот же расчёт, что в `churn.ipynb`) |
| `add_target` | целевая переменная (нужна только для переобучения) |
| `make_model` | создаёт модель с параметрами из `model_params.json` |
| `top_factors` | три признака, сильнее всего повышающих риск клиента |
| `train` | переобучение на свежей выгрузке |
| `score` | прогноз риска на дату |

Режимы запуска:

```bash
python churn_pipeline.py score                    # прогноз на утро после последнего дня выгрузки
python churn_pipeline.py score --date 2026-09-15  # прогноз на конкретную дату
python churn_pipeline.py train                    # переобучение на свежей выгрузке
```

Параметры: `--data-dir` (по умолчанию `data/raw`), `--model-dir` (`models`), `--out-dir` (`results`).

При переобучении (`train`) модель учится на всех данных с известным исходом, кроме последних
трёх месяцев — на них заново подбирается порог тревоги с тем же бюджетом тревог.

### `models/model_params.json`

| поле | что значит |
|---|---|
| `model` | какая модель выбрана: `catboost_optuna` или `logreg_optuna` |
| `params` | подобранные optuna гиперпараметры |
| `threshold` | порог тревоги: риск выше — тревога |
| `alert_share` | бюджет тревог — доля клиенто-дней с тревогой, по которой выбран порог |
| `feature_cols` | список признаков в том порядке, в каком их ждёт модель |

### `results/churn_risk_YYYY-MM-DD.csv`

| колонка | что значит |
|---|---|
| `client_id` | клиент |
| `date` | дата прогноза (утро; используется активность по предыдущий день) |
| `risk` | оценка риска расторжения в ближайшие 28 дней (для ранжирования, не калиброванная вероятность) |
| `alert` | тревога: риск выше порога — стоит связаться с клиентом |
| `factor_1..3` | признаки, сильнее всего повышающие риск — наблюдаемые сигналы, не доказанные причины |

## 3. Как файлы связаны

```
data/raw/*.csv
   │
   ├──► churn.ipynb ───────────────► models/churn_model.pkl
   │      (исследование,               models/model_params.json
   │       подбор модели)                   │            │
   │                                        │            │
   ├──► churn_anomaly.ipynb ◄───────────────┘            │
   │      (2-й подход, сравнение)                        │
   │        ▲                                            │
   │        │ импортирует функции признаков              │
   │        │                                            ▼
   └──► churn_pipeline.py ──── score ──────────► results/churn_risk_YYYY-MM-DD.csv
                          └─── train ──► перезаписывает models/
```

- **`churn.ipynb` → `models/`**: ноутбук выбирает модель и сохраняет её. Без этого шага скрипт не запустится.
- **`models/` → `churn_pipeline.py`**: `score` берёт модель и порог, `train` берёт тип модели и параметры.
- **`churn_pipeline.py` → `churn_anomaly.ipynb`**: второй ноутбук импортирует из скрипта функции подготовки данных.
- **`models/` → `churn_anomaly.ipynb`**: второй ноутбук загружает модель первого подхода для сравнения.

## 4. Порядок запуска

### Первый раз

```bash
cd ~/Desktop/interfax/churn
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

1. Положить три CSV в `data/raw/`.
2. Открыть `churn.ipynb`, выбрать ядро `.venv`, **Run All** (подбор optuna — несколько минут).
   Появится папка `models/`.
3. Открыть `churn_anomaly.ipynb`, **Run All** (около 20 секунд) — сравнение подходов.
4. Проверить скрипт: `python churn_pipeline.py score` — появится `results/churn_risk_….csv`.

### В работе у заказчика

| когда | что запускать |
|---|---|
| каждое утро | выгрузить активность по вчерашний день → `python churn_pipeline.py score` |
| раз в месяц–квартал | свежая выгрузка → `python churn_pipeline.py train` |
| если меняется набор признаков или модель | заново `churn.ipynb` (пересохранит `models/`) |

Ежедневный запуск удобно повесить на Airflow: DAG из двух задач «выгрузка → score».

## 5. Что где менять

| что хотите поменять | где |
|---|---|
| горизонт прогноза, окна признаков, окно нормы | константы в начале **и** `churn.ipynb`, **и** `churn_pipeline.py` — значения должны совпадать |
| длину valid и test | `TEST_MONTHS`, `VALID_MONTHS` в `churn.ipynb` и `churn_anomaly.ipynb` |
| набор признаков | расчёт в `churn.ipynb` и функция `build_features` в `churn_pipeline.py`, затем перезапустить `churn.ipynb` |
| бюджет тревог | выбирается в `churn.ipynb` (раздел «Поиск порога тревоги»), сохраняется в `model_params.json` |
| папки с данными / моделью / результатами | параметры `--data-dir`, `--model-dir`, `--out-dir` скрипта |

Расчёт признаков написан в двух местах: развёрнуто с пояснениями в `churn.ipynb` и компактно
в `churn_pipeline.py`. Если меняете один — меняйте и второй. Сейчас они совпадают
на всех строках и признаках (проверено).

## 6. Ключевые правила (защита от утечек)

- Прогноз на утро дня использует активность не позднее предыдущего дня.
- `churn_date` и `outcome_observed_until` — только для разметки таргета, не признаки.
- `target = 0` ставится, только если все 28 дней после даты прогноза наблюдались;
  последние 28 дней выгрузки у неушедших клиентов в обучение не идут.
- Нулевая активность восстанавливается только в дни действующего договора.
- `history_days` (дни истории в выгрузке) в модель не берётся — фактически это дата прогноза.
- Разбиение на train / valid / test и кросс-валидация — по времени, с зазором 28 дней.

## 7. Итоги

| подход | ROC-AUC (test) | пойманы за 14–28 дней | ложные тревоги |
|---|---|---|---|
| CatBoost (с учителем) — основная модель | 0.875 | 72% | 22% |
| правило по личной норме (без учителя) | 0.877 | 78% | 13% |
| Isolation Forest (без учителя) | 0.870 | 72% | 21% |

Подходы сопоставимы по качеству (различия — один-два клиента). Подробные выводы — в конце
`churn.ipynb` и `churn_anomaly.ipynb`.
